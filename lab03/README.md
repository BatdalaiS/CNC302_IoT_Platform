## 1. Зорилго

Гурван зүйлийг **тоогоор** тогтооно:

1. MQTT 5.0-ийн шинэ боломжууд юу шийддэг вэ — 3.1.1-тэй харьцуулахад

Лабын гол бүтээгдэхүүн: **таны багийн төслийн UNS схем** ба **QoS сонголтын үндэслэл**. Энэ хоёрыг Лаб 4-өөс эцэс хүртэл ашиглана.

## 3. Онолын сануулга

**QoS бол найдвартай байдлын баталгаа биш, дамжуулалтын гэрээ.**

| QoS | Гэрээ | Гар барилт | Давхардах уу | Алдагдах уу |
|---|---|---|---|---|
| 0 | at most once | PUBLISH | үгүй | **тийм** |
| 1 | at least once | PUBLISH → PUBACK | **тийм** | үгүй |
| 2 | exactly once | PUBLISH → PUBREC → PUBREL → PUBCOMP | үгүй | үгүй |

QoS 2 нь дөрвөн алхамт гар барилт тул хамгийн удаан. Гэхдээ **энэ нь зөвхөн брокер хүртэлх баталгаа**. Брокероос цааш өгөгдлийн сан руу бичихэд алдаа гарвал QoS 2 ч аврахгүй. Энэ ойлголт Лаб 5-ын эвдрэлийн туршилтад чухал.

**Burst vs steady-state.** 500 мессежийг нэг дор шидвэл хэмжсэн "саатал" нь үнэндээ **дараалалд хүлээсэн хугацаа**. Тогтвортой урсгал (`--interval`)-д хэмжсэн саатал нь **жинхэнэ сүлжээ + брокерын саатал**. Хоёулаа хэрэгтэй, гэхдээ ялгааг ойлгох ёстой.

**Unified Namespace.** UNS бол технологи биш, **гэрээ**. "Аливаа өгөгдөл яг нэг л газар, урьдчилан таамаглах боломжтой нэрээр байрлана" гэсэн тохиролцоо. Схемгүй бол 2 жилийн дараа таны брокер дээр `temp`, `Temperature`, `temp_c`, `sensor/1/t` гэсэн дөрвөн өөр нэр зэрэг оршино.

## 4. Алхмууд

### Алхам 1 — MQTT 5.0-ийн зургаан боломж (60 мин)

Бүгдийг дараалан ажиллуулж, гаралтыг тайландаа хадгална.

```bash
cd ~/cnc302        # зөөврийн компьютер дээр, .venv идэвхтэй
H=pi-team03.local

python lab03/mqtt5_features.py --host $H expiry  --expiry 10
python lab03/mqtt5_features.py --host $H alias   --count 1000
python lab03/mqtt5_features.py --host $H reqresp
python lab03/mqtt5_features.py --host $H shared  --subs 3 --count 300
python lab03/mqtt5_features.py --host $H session --expiry 60
python lab03/mqtt5_features.py --host $H reason
```

**Хүснэгт 1**-ийг бөглөнө: боломж бүрд *ямар асуудлыг шийдэж байна вэ*, *MQTT 3.1.1-д үүнийг хэрхэн шийддэг байсан бэ*, *бидний төсөлд хэрэгтэй юу*.

**Alias-ийн туршилт (хэмжилттэй).** EMQX самбар → **Monitoring → Metrics** дээр `Bytes Received` утгыг тэмдэглээд:

```bash
# alias-гүйгээр 1000 мессеж
python tools/sim_device.py --host $H --devices 1 --count 1000 --interval 0 \
  --topic-prefix cnc302 --site ulaanbaatar --area campus-north-building-a-floor-3
```
Дахин `Bytes Received`-ийг тэмдэглэнэ. Дараа нь `alias` туршилтыг ажиллуулаад дахин тэмдэглэнэ. **Хүснэгт 2**.

### Алхам 2 — QoS-ийн хэмжилт: burst ба steady-state (50 мин)

**2.1 Burst (дараалалд хүлээх)** — `--interval 0`:

```bash
python tools/qos_latency.py --host $H --sweep --count 500 --payload 200 \
    --csv lab03/out/qos-burst.csv
```

**2.2 Steady-state (жинхэнэ саатал)** — 100 мсж/с:

```bash
python tools/qos_latency.py --host $H --sweep --count 500 --payload 200 \
    --interval 0.01 --csv lab03/out/qos-steady.csv
```

**2.3 Ачааллын хэмжээний нөлөө** — 200 Б ба 2000 Б:

```bash
python tools/qos_latency.py --host $H --qos 1 --count 500 --payload 2000 \
    --interval 0.01 --csv lab03/out/qos-2000b.csv
```

**2.4 Хуваалцсан захиалгын нөлөө:**

```bash
python tools/qos_latency.py --host $H --qos 1 --count 500 --interval 0.01 \
    --shared 3 --csv lab03/out/qos-shared3.csv
```

**Хүснэгт 3** ба **Хүснэгт 4**-ийг бөглөнө.

> **Ажигла:** burst горимд p50 нь 30–50 мс байхад steady-state горимд 1 мс-ээс бага байж магадгүй. Энэ 30 дахин ялгаа **брокерын гэм биш** — та өөрөө дарааллыг дүүргэсэн. Тайландаа энэ ялгааг тайлбарлана.

### Алхам 3 — Unified Namespace схем зохиох ба шалгах (45 мин)

**3.1 Одоогийн байдлыг харах.** Виртуал флотыг ажиллуулж байхад:

```bash

**3.2 Зөрчил үүсгэж, шалгагч барьж авахыг харах:**

mosquitto_pub -h $H -t 'sensors/room12/temperature' -m '24'
mosquitto_pub -h $H -t 'cnc302/ub/campus/line01/dev1/telemetry/raw' -m '{}'
```

Эдгээрийг **шалгагч ажиллаж байх зуур** илгээнэ. Гаралтыг тайланд хуулна.

**3.3 Багийн төслийн UNS схемээ зохионо.** `lab03/uns-schema.md` файлд:

- Таны төслийн шатлал (site / area / line / device) юу гэсэн үг вэ?
- Ямар суваг (channel) хэрэгтэй вэ — `telemetry`, `status`, `cmd`, `event`, `attributes`-ээс аль нь?
- Хадгалагдах (retained) сэдвүүд аль нь вэ? Яагаад?
- Тушаал (command) хаашаа очих вэ? Хариу хаанаас ирэх вэ?
- 10 жилийн дараа шинэ талбай нэмэхэд схем эвдрэх үү?

Дор хаяж **10 бодит сэдвийн жишээ** бичнэ.

**3.4 Схемээ шалгуулах.** `uns_tree.py`-ийн `--strict` горим нь CI-д ашиглаж болно:

```bash
python lab03/uns_tree.py --host $H --seconds 20 --strict --prefix cnc302
echo "гарах код: $?"     # 0 = цэвэр, 1 = зөрчилтэй
```

> Энэ бол жижиг ч чухал санаа: **нэршлийн дүрмийг автоматаар шалгаж болно**. Багийн төсөлд үүнийг CI-д оруулбал схем аяндаа сахигдана.

### Алхам 4 — Sparkplug B (45 мин)

⚠ `sparkplug_lite.py` нь protobuf-гүй **хялбаршуулсан** хувилбар. Сэдвийн бүтэц, төлөвийн машин, seq нь стандартын дагуу; ачаалал нь JSON.

**4.1 Хоёр терминалд зэрэг:**

```bash
# терминал 1 — ажиглагч (платформ)
python lab03/sparkplug_lite.py monitor --host $H --seconds 90

# терминал 2 — ирмэгийн зангилаа
python lab03/sparkplug_lite.py node --host $H --devices 3 --seconds 60 --interval 1
```

Ажигла: **NBIRTH → DBIRTH → DDATA … → NDEATH**. DDATA дотор метрикийн **нэр байхгүй, зөвхөн alias** байгааг анзаар. Ажиглагч нь BIRTH-ээс сурсан хүснэгтээрээ нэрийг сэргээнэ.

**4.2 Дарааллын тасалдал үүсгэх:**

```bash
python lab03/sparkplug_lite.py node --host $H --devices 2 --seconds 30 --drop-seq 5
```

Ажиглагч `⚠ ДАРААЛЛЫН ТАСАЛДАЛ` гэж мэдээлэх ёстой.

**4.3 Гэнэтийн салалт (Last Will).** Зангилааг ажиллуулаад **Ctrl+C-гүйгээр** терминалыг хааж алах:

```bash
python lab03/sparkplug_lite.py node --host $H --devices 2 --seconds 300 &
sleep 15
kill -9 %1        # гэнэт унтарлаа
```

Ажиглагч дээр `NDEATH` **автоматаар** гарах ёстой — учир нь брокер өөрөө Last Will-ийг нийтэлнэ. Хэдэн секундын дараа гарсныг тэмдэглэ (keepalive-тай холбоотой).

**4.4 Report-by-exception.** `--deadband` ашиглаж зөвхөн өөрчлөгдсөн утгыг илгээнэ:

```bash
python lab03/sparkplug_lite.py node --host $H --devices 3 --seconds 30 --deadband 0.5
```

Deadband 0 ба 0.5 үед илгээсэн DDATA-гийн тоог харьцуулна. **Хүснэгт 5**.

## 6. Хяналтын асуулт

1. QoS 2 нь QoS 1-ээс хэдэн дахин удаан байв? Энэ ялгаа зөвхөн гар барилтын алхмаас үүдэлтэй юу?
2. Burst ба steady-state саатлын ялгааг тайлбарла. Аль нь SLA-д бичихэд тохиромжтой вэ?
3. Батарейгаар ажилладаг төхөөрөмжид QoS 2 хэрэглэх нь ямар үнэтэй вэ? (Санамж: сэрүүн байх хугацаа, радио дамжуулалтын тоо.)
4. Session Expiry-г 24 цаг болговол брокерын санах ойд юу болох вэ? 1000 төхөөрөмж дээр тооцоолж үзнэ үү.
5. Shared subscription нь хэрэглэгчийг өргөтгөх боломж өгдөг. Гэхдээ мессежийн **дараалал** (ordering) юу болох вэ?
6. Message Expiry ба Session Expiry хоёрын ялгаа юу вэ? Аль нь ямар асуудал шийддэг вэ?
7. UNS схемгүйгээр 3 жил ажилласан систем дээр шинэ хэрэглэгч нэмэхэд ямар бэрхшээл гарах вэ?
8. Sparkplug B-гийн birth certificate байхгүй бол платформ шинээр холбогдоход юу мэдэхгүй вэ?
9. Sparkplug-ийн seq дугаар 256 дээр эргэлддэг. 1000 мсж/с урсгалд энэ хэр хурдан эргэх вэ? Асуудал болох уу?
10. `uns_tree.py --strict`-ийг CI-д оруулбал ямар ашиг гарах вэ? Ямар сул тал байна вэ?
