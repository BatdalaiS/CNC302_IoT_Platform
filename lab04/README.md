## 1. Зорилго

Энэ бол хичээлийн **гол лаборатори**. Хоёр асуултад тоон хариулт өгнө:

1. Мессежийг **хаана** боловсруулах вэ — брокер дээр үү, платформ дээр үү, хэрэглэгч дээр үү?
2. Нэг Raspberry Pi 5 **хэдэн төхөөрөмж** даах вэ? Хязгаар нь юу вэ — CPU, санах ой, эсвэл холболтын тоо?

Лаб 1-д та шугаман экстраполяциар таамаг гаргасан. Өнөөдөр түүнийг **бодитоор шалгана**. Таамаг зөв гарах албагүй — буруу гарвал тэр нь илүү сонирхолтой үр дүн.

> **Анхаар:** энэ лабораторийг бичгийн тайлангаар биш, **үзүүлэнгээр** үнэлнэ. Багийн гурван гишүүн бүгд ярина. Слайд шаардлагагүй — ажиллаж буй график, тоо л хангалттай.

## 3. Онолын сануулга

**Мессежийг хаана боловсруулах вэ?**

| Байрлал | Давуу тал | Сул тал |
|---|---|---|
| Брокер дээр (EMQX Rule Engine) | хамгийн бага саатал, нэмэлт сүлжээний давхарга үгүй | брокерын CPU иднэ, дүрэм нь SQL-ээр хязгаарлагдмал |
| Платформ дээр (ThingsBoard Rule Chain) | баялаг логик, төхөөрөмжийн контексттэй | нэмэлт үсрэлт, ThingsBoard-ын JVM ачаалагдана |
| Тусдаа хэрэглэгч (Node-RED, Python) | бүрэн уян хатан, тусдаа өргөтгөнө | хамгийн их саатал, ажиллуулах нэмэлт үйлчилгээ |

Энэ шийдвэрийг **зөн совингоор биш, хэмжилтээр** гаргах ёстой. Өнөөдөр гурвуулангийнх нь саатлыг хэмжинэ.

**Хэвтээ ба босоо өргөтгөл.** Pi 5-ыг "илүү том" болгож чадахгүй (босоо өргөтгөл боломжгүй). Тиймээс цорын ганц зам бол **хэвтээ** — олон зангилаа. Гэхдээ өргөтгөхийн өмнө **хаана мөргөж байгааг** мэдэх ёстой.

**Саturation (ханалт).** Систем ачаалал нэмэгдэхэд эхлээд шугаман өснө, дараа нь тэгширнэ, эцэст нь **буурна**. Сүүлийн үе шат хамгийн аюултай: систем ажиллаж байгаа мэт харагдаад бодит хүчин чадал нь буурна. Үүнийг олж харах нь энэ лабораторийн гол зорилго.

## 4. Алхмууд

### Алхам 1 — EMQX Rule Engine (40 мин)

**1.1** EMQX самбар (`:18083`) → **Integration → Rules → Create**.

Дүрэм 1 — чичиргээний хэт өндөр утгыг шүүх:

```sql
SELECT
  payload.device_id      as device_id,
  payload.vibration_rms  as vibration,
  payload.temperature    as temperature,
  clientid               as source,
  timestamp              as ts
FROM
  "cnc302/+/+/+/+/telemetry"
WHERE
  payload.vibration_rms > 1.5
```

Үйлдэл (Action) нэмнэ: **Republish** → сэдэв `cnc302/alerts/vibration`.

**1.2** Дүрмийг туршина:

```bash
# терминал 1 — дохиоллыг сонсоно
mosquitto_sub -h $H -t 'cnc302/alerts/#' -v

# терминал 2 — гажилтай өгөгдөл илгээнэ
python tools/sim_device.py --host $H --devices 5 --interval 1 --anomaly-rate 0.2
```

**1.3 Саатлыг хэмжинэ.** Дүрмийн боловсруулалт хэдэн миллисекунд нэмэв? EMQX самбарын дүрмийн статистик (`Matched`, `Failed`, `Rate`) хэсгээс уншина. **Хүснэгт 1**.

**1.4** Дүрэм 2 — нэгтгэл (window). EMQX-ийн SQL нь цонхны функцийг хязгаартай дэмждэг. Оролдож үзээд **боломжгүйг батал** — энэ нь Лаб 5-д Node-RED хэрэгтэй болох шалтгаан:

```sql
SELECT avg(payload.temperature) as avg_temp
FROM "cnc302/+/+/+/+/telemetry"
GROUP BY device_id, INTERVAL 60s   -- ← EMQX CE-д дэмжигдэх үү? Шалга.
```

Үр дүнг тайландаа тэмдэглэ.

### Алхам 2 — ThingsBoard Rule Chain (30 мин)

**2.1** ThingsBoard → **Rule chains → Root Rule Chain**.

Гинжийг бүтээнэ: `Message Type Switch` → `Script (filter)` → `Create Alarm`.

Script зангилааны фильтр:
```javascript
return msg.vibration_rms > 1.5;
```

`Create Alarm` зангилаад: төрөл `HighVibration`, ноцтой байдал `MAJOR`.

**2.2** Лаб 2-т үүсгэсэн төхөөрөмжөөр туршина (ThingsBoard-ын MQTT нь **1884** порт):

```bash
python tools/sim_device.py --host $H --port 1884 --devices 3 \
  --username <ACCESS_TOKEN> --anomaly-rate 0.3 --interval 1 \
  --topic-prefix v1/devices/me
```

> ThingsBoard нь `v1/devices/me/telemetry` сэдэв хүлээдэг тул UNS сэдэв энд ажиллахгүй. Энэ өөрөө чухал ажиглалт: **платформ бүр өөрийн сэдвийн гэрээтэй**. UNS-ийг платформын гэрээтэй хэрхэн холбохыг тайландаа бод.

**2.3** ThingsBoard-ын **Alarms** хэсэгт дохиолол үүссэнийг шалга. Саатлыг хэмжинэ: телеметр илгээснээс дохиолол гарах хүртэл. **Хүснэгт 1**-ийн 2-р мөр.

### Алхам 4 — Шат дараалсан ачааллын тест (75 мин)

**Хамгийн чухал алхам.** Хоёр терминалыг зэрэг ажиллуулна:

```bash
# Pi дээр — хэмжилт цуглуулагч (аль хэдийн ажиллаж байна)
# Зөөврийн компьютер дээр:
bash lab04/loadtest.sh ramp pi-team03.local
```

Шатууд: **10 → 50 → 100 → 250 → 500 → 1000** холболт, тус бүр 1 мсж/с, 120 секунд.

**Шат бүрд тэмдэглэ (Хүснэгт 2):**
- emqtt-bench-ийн мэдээлсэн бодит илгээх хурд
- EMQX-ийн хүлээн авсан хурд
- CPU %, сул санах ой, температур
- Алдагдсан мессеж (`emqx_msg_dropped`)

**Хэзээ зогсоох вэ.** Дараах шинж тэмдгийн аль нэг гарвал шатыг зогсоож, тэр цэгийг **хязгаар** гэж тэмдэглэнэ:

| Шинж тэмдэг | Утга |
|---|---|
| Хүлээн авсан хурд < илгээсэн хурдын 95% | брокер гүйцэхгүй байна |
| `emqx_msg_dropped` > 0 | мессеж хаягдаж эхлэв |
| Сул санах ой < 300 MiB | OOM ойрхон |
| `throttled` ≠ `0x0` | Pi халж давтамжаа бууруулав — **хэмжилт хүчингүй** |
| CPU > 380% (4 цөм × 100%) | CPU ханалаа |

> **Хэрэв 1000 холболт хүртэл ямар ч асуудалгүй бол:** сайн байна! Ачааллыг нэмнэ — `-I 500` (2 мсж/с) эсвэл `-c 2000`. Хязгаарыг олох хүртэл үргэлжлүүлнэ.

### Алхам 6 — Багтаамжийн томьёо (20 мин)

Хэмжилтэд тулгуурлан **Хүснэгт 4**-ийг бөглөж, дараах томьёог гаргана:

```
Хэрэгтэй Pi-ийн тоо  =  ⌈ N_төхөөрөмж × R_мсж/с ⌉ / C_нэг_Pi × S

  N  — төхөөрөмжийн тоо
  R  — нэг төхөөрөмжийн мессежийн хурд
  C  — нэг Pi-ийн хэмжсэн багтаамж (мсж/с), 70% ашиглалтаар
  S  — аюулгүйн коэффициент (санал: 1.5)
```

**Практик даалгавар:** Таны багийн төслийн хэрэглээнд (жишээ нь ухаалаг кампусын 400 өрөө × 3 мэдрэгч × 12 мсж/цаг) хэдэн Pi хэрэгтэй вэ? Тооцоог үзүүлэнд оруулна.

## 8. Үнэлгээний шалгуур (10 оноо, үзүүлэнгээр)

| Шалгуур | Оноо |
|---|---|
| Rule Engine хоёр платформ дээр ажиллаж, саатал хэмжигдсэн | 2 |
| Ачааллын тест бүрэн шатаар гүйцэтгэгдэж хязгаар олдсон | 3 |
| Ачааллын муруй ба ханалтын шинжилгээ | 2 |
