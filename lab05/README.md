## 1. Зорилго

Бүрэн өгөгдлийн шугам барьж, дараа нь **зориудаар эвдэж** юу алдагдахыг тоогоор хэмжинэ.

```
   MQTT  →  Node-RED  →  InfluxDB 3  →  Grafana
              (шүүх,        (хадгалах)     (харах)
               нэгтгэх)
```

Ихэнх сургалтын лаборатори эхний мөрөөр л дуусдаг: "шугам ажиллаж байна ✓". Гэвч бодит систем **эвдэрдэг**. Тиймээс энэ лабораторийн хоёр дахь хагаст бид брокерыг унтрааж, сүлжээг тасалж, дискийг дүүргэж, **юу алдагдаж, юу буферлэгдэж, юу автоматаар сэргэхийг** хэмжинэ.

### Гол бүтээгдэхүүн: эвдрэлийн матриц

| эвдрэл | шинж тэмдэг | өгөгдлийн алдагдал | сэргэх хугацаа |
|---|---|---|---|

Энэ хүснэгт бол таны системийн **найдвартай байдлын паспорт**. Багийн төслийн тайланд шууд орно.

## 3. Онолын сануулга

**QoS нь брокер хүртэл л баталгаа өгнө.** QoS 2-оор илгээсэн мессеж брокерт баттай хүрнэ. Гэхдээ брокероос Node-RED, тэндээс InfluxDB руу явах замд баталгаа **байхгүй**. Энэ бол Лаб 3-т үзсэн ойлголтын практик үр дагавар: **төгсгөлөөс төгсгөл хүртэлх баталгаа нь давхарга бүрийн баталгааны үржвэр биш, хамгийн сул холбоосоор тодорхойлогдоно**.

**Хаана буферлэгдэх вэ?**

| Эвдрэл | Хэн буферлэдэг | Хязгаар |
|---|---|---|
| Брокер унтарсан | төхөөрөмж өөрөө (хэрэв кодлогдсон бол) | төхөөрөмжийн RAM |
| Хэрэглэгч унтарсан | брокер (сесс хадгалагдсан бол) | `max_mqueue_len` |
| Өгөгдлийн сан унтарсан | Node-RED (dead-letter бичвэл) | диск |
| Диск дүүрсэн | **хэн ч үгүй** | — |

Сүүлийн мөр хамгийн аюултай: диск дүүрэхэд бүх давхарга нэгэн зэрэг унана.

**Сэргэх хугацаа (MTTR) vs өгөгдлийн алдагдал (RPO).** Хоёр өөр үзүүлэлт. Систем 30 секундын дараа сэргэж болно (сайн MTTR), гэхдээ тэр 30 секундын өгөгдөл бүрэн алдагдсан байж болно (муу RPO).

## 4. Алхмууд

### Алхам 1 — Өгөгдлийн сан бэлтгэх (20 мин)

InfluxDB 3-д мэдээллийн сан үүсгэнэ:

```bash
curl -s -X POST 'http://localhost:8181/api/v3/configure/database' \
  -H 'Content-Type: application/json' -d '{"db":"cnc302"}'

# шалгах
curl -s 'http://localhost:8181/api/v3/configure/database?format=json' | jq
```

Гараар нэг мөр бичиж туршина:

```bash
curl -s -X POST 'http://localhost:8181/api/v3/write_lp?db=cnc302&precision=millisecond' \
  -H 'Content-Type: text/plain' \
  --data-binary "telemetry,site=test,device=test0 temperature=24.5 $(date +%s%3N)"

curl -s -X POST 'http://localhost:8181/api/v3/query_sql' \
  -H 'Content-Type: application/json' \
  -d '{"db":"cnc302","q":"SELECT * FROM telemetry LIMIT 5","format":"json"}' | jq
```

> InfluxDB 2.7 нөөц хувилбар ашиглаж байгаа бол `docs/troubleshooting.md`-ийн заавраар. Дараагийн алхмуудад `--influx2` тугийг нэмнэ.

### Алхам 2 — Node-RED шугам барих (50 мин)

**2.1 Импортлох.** Node-RED (`:1880`) → цэс (☰) → **Import** → `lab05/flows/nodered-pipeline.json` файлын агуулгыг наана.

Урсгалын бүтэц:

```
mqtt in ──▶ задлан шинжлэх ─┬─▶ line protocol (түүхий) ─┐
                            │                           ├─▶ InfluxDB бичих ─▶ шалгах ─┬─▶ (ok)
                            └─▶ 60с цонх ─▶ lp (нэгтгэл)┘                              └─▶ dead-letter
```

**2.2 Брокерын тохиргоог шалгана.** `mqtt-broker` зангилаа дээр давхар товшиж `emqx:1883` эсэхийг батална (Docker сүлжээн дотор үйлчилгээний нэрээр хандана).

**2.3 Deploy** дараад өгөгдөл урсгана:

```bash
python tools/sim_device.py --host $H --devices 10 --interval 1
```

Node-RED-ийн debug самбарт 10 секунд тутам `write_ok` тоолуур өсөх ёстой.

**2.4 Задлан шинжлэх зангилааны гурван үүргийг ойлгоно:**

| Үүрэг | Код дотор | Яагаад |
|---|---|---|
| UNS схемийн шалгалт | `if (p.length !== 6)` | буруу нэршилтэй өгөгдөл санд орохоос сэргийлнэ |
| Өгөгдлийн чанар | `temperature < -60 \|\| > 150` | эвдэрсэн мэдрэгчийн утга нэгтгэлийг сүйтгэнэ |
| Шошго гаргах | `msg.tags = {site, area, line, device}` | InfluxDB-д индексжүүлэх хэмжээсүүд |

**2.5 Чанарын шалгуурыг туршина.** Хүрээнээс гарсан утга илгээнэ:

```bash
mosquitto_pub -h $H -t 'cnc302/ulaanbaatar/campus/line01/dev9999/telemetry' \
  -m '{"ts":'"$(date +%s%3N)"',"temperature":9999,"humidity":50,"vibration_rms":0.3}'
```

Node-RED-д `warn` гарч, өгөгдөл сан руу **орохгүй** байх ёстой. Шалгана:

```bash
curl -s -X POST 'http://localhost:8181/api/v3/query_sql' -H 'Content-Type: application/json' \
  -d '{"db":"cnc302","q":"SELECT count(*) c FROM telemetry WHERE device='"'"'dev9999'"'"'","format":"json"}'
```

**2.6 Хадгалах бодлого.** InfluxDB 3-д:

```bash
curl -s -X POST 'http://localhost:8181/api/v3/configure/database' \
  -H 'Content-Type: application/json' \
  -d '{"db":"cnc302_30d","retention_period":"30d"}'
```

**Хүснэгт 1**-ийг бөглөнө: түүхий өгөгдөл хэдэн хоног, нэгтгэсэн өгөгдөл хэдэн хоног, яагаад?

### Алхам 3 — Grafana самбар (25 мин)

Grafana (`:3000`) → өгөгдлийн эх сурвалж аль хэдийн тохируулагдсан (`stack/grafana/provisioning`).

Гурван панель үүсгэнэ:

| Панель | Асуулга |
|---|---|
| Температурын цуваа | `SELECT time, temperature, device FROM telemetry WHERE $__timeFilter(time)` |
| Идэвхтэй төхөөрөмж | `SELECT count(DISTINCT device) FROM telemetry WHERE $__timeFilter(time)` |
| Бичилтийн хурд | `SELECT time, count(*) FROM telemetry WHERE $__timeFilter(time) GROUP BY time` |

**Дохиолол нэмнэ:** дундаж чичиргээ > 1.5 үед. Alerting → New alert rule.

### Алхам 4 — ЭВДРЭЛИЙН ТУРШИЛТ (90 мин)

**Энэ бол лабораторийн гол хэсэг.** Туршилт бүр ижил бүтэцтэй:

```
1. data_integrity.py publish эхлүүлнэ (5 минут)
2. 60 секундын дараа эвдрэл үүсгэнэ
3. Тестийг дуустал хүлээнэ
4. verify-ээр алдагдлыг тоолно
```

#### 4.1 Суурь (эвдрэлгүй) — заавал эхлээд хийнэ

```bash
# зөөврийн компьютер дээр
python lab05/data_integrity.py publish --host $H --rate 10 --seconds 180 \
    --qos 1 --run-id base --outdir lab05/out
python lab05/data_integrity.py verify --influx http://$H:8181 --run-id base \
    --outdir lab05/out
```

**Алдагдал 0% байх ёстой.** Хэрэв суурь дээр аль хэдийн алдагдаж байвал цааш явах утгагүй — шугамаа засна.

#### 4.2 Брокер унтарсан

```bash
# терминал 1 (зөөврийн компьютер)
python lab05/data_integrity.py publish --host $H --rate 10 --seconds 300 \
    --qos 1 --run-id broker30 --outdir lab05/out

# терминал 2 (Pi дээр, 60 секундын дараа)
cd ~/cnc302 && bash lab05/failure_inject.sh broker 30
```

Ажигла: publish терминалд `⚠ холболт тасарлаа` → `✓ дахин холбогдлоо`.

```bash
python lab05/data_integrity.py verify --influx http://$H:8181 --run-id broker30
```

#### 4.3 Өгөгдлийн сан унтарсан (брокер ажиллаж байна!)

```bash
python lab05/data_integrity.py publish --host $H --rate 10 --seconds 300 \
    --qos 1 --run-id influx30 --outdir lab05/out
# Pi дээр:
bash lab05/failure_inject.sh influx 30
```

> **Энэ хамгийн сонирхолтой тохиолдол.** Төхөөрөмж юу ч анзаарахгүй — брокер хүлээж авсаар байна. Гэвч Node-RED-ийн бичилт унана. Dead-letter файл ажиллаж байна уу?

```bash
docker exec cnc302-nodered wc -l /data/deadletter.jsonl
```

#### 4.4 Сүлжээ тасарсан

```bash
python lab05/data_integrity.py publish --host $H --rate 10 --seconds 300 \
    --qos 1 --run-id net30 --outdir lab05/out
bash lab05/failure_inject.sh network 30
```

#### 4.5 Диск дүүрсэн (аюулгүй давталтын файлаар)

```bash
bash lab05/failure_inject.sh disk 60
```

Энэ хооронд Docker-ийн логийн хязгаар ажиллаж байгааг шалгана:
```bash
docker inspect cnc302-emqx --format '{{json .HostConfig.LogConfig}}'
sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail -3
```

#### 4.6 CPU ханалт

```bash
python lab05/data_integrity.py publish --host $H --rate 50 --seconds 180 \
    --qos 1 --run-id cpu45 --outdir lab05/out

```

#### 4.7 QoS-ийн нөлөө

Брокерын унтралтыг **QoS 0-оор** давтана:


## 6. Хяналтын асуулт

1. QoS 1 ба QoS 0-ын хооронд брокер унтарсан үед алдагдал хэр ялгаатай байв? Хүлээсэн үр дүнтэй тань таарсан уу?
2. Өгөгдлийн сан унтарсан үед **төхөөрөмж** юу ч анзаарсангүй. Энэ яагаад аюултай вэ? Хэрхэн илрүүлэх вэ?
3. Хамгийн урт тасалдал ба эвдрэлийн үргэлжлэх хугацаа тэнцүү байсан уу? Хэрэв тасалдал урт бол илүүдэл хугацаа хаанаас гарав?
4. Dead-letter загвар юу шийдэж, юу шийдэхгүй вэ?
5. Диск дүүрсэн үед аль үйлчилгээ хамгийн түрүүнд унав? Логийн эргэлт тохируулаагүй байсан бол юу болох байсан бэ?
6. MTTR ба RPO-гийн аль нь таны багийн төслийн хэрэглээнд илүү чухал вэ? Яагаад?
7. Төгсгөлөөс төгсгөл хүртэлх баталгааг сайжруулах гурван арга санал болго. Тус бүрийн зардлыг дурд.
8. Эдгээр туршилтыг **үйлдвэрлэлийн** системд хэрхэн аюулгүйгээр хийх вэ? (Санамж: chaos engineering, blast radius.)
